# 劳动学时管理系统 - 项目业务规则基准

> 本文件是整个项目的业务规则基准，后续所有阶段开发都必须先读取本文件。
> 未经评审确认，不得擅自改变本文件中的业务规则，也不得擅自增加需求。

---

## 一、项目开发原则

### 1. 不擅自增加业务

后续开发必须以已经确认的业务规则为准。

不要因为认为"以后可能用到"就增加数据库表、接口或复杂业务。

### 2. 数据历史必须保留

核心业务数据原则上禁止物理删除。

包括但不限于：

- 学生
- 学生学期档案
- 班级历史
- 考勤
- 补课
- 助教记录
- 额外参加
- 成绩
- 重修
- 换证考试
- 操作日志

需要取消或失效时使用 status 等状态字段，禁止使用物理删除破坏业务历史。

### 3. 后端必须进行权限校验

不能只通过前端隐藏按钮实现权限。

- 教师只能操作自己负责的班级
- 助教只能操作被授权班级
- 超级管理员拥有全局管理权限

所有涉及班级范围的数据操作，都必须在 Service 层进行后端权限校验。

### 4. 不允许用前端数据作为权限依据

例如：

前端传入 classId=1，

后端不能直接认为当前教师拥有 1 班权限。

必须查询当前用户实际负责班级后再允许操作。

## 二、核心业务规则

### 1. 学生

- 学生不是系统登录用户
- 学生是业务数据对象
- 助教本质上仍然是学生
- 助教账号通过 sys_user.student_id 关联学生

### 2. 教师

- 教师只能查看和操作自己负责的班级
- 超级管理员可以操作全部数据

### 3. 助教

- 助教只能操作被授权的班级和节次范围
- 助教不能给自己评分
- 助教身份发生变化时保留历史记录
- 不能通过删除学生记录来处理助教身份变化

### 4. 劳动课程

- 劳动课程按学期管理
- 课程由多个固定节次组成
- 当前默认要求 11 次，但数据库必须允许配置

### 5. 课程延期

课程延期时：

- session_no 不能改变
- planned_date 保留原计划日期
- actual_date 保存实际发生日期
- 延期不会额外增加课程次数
- 封存时间从 actual_date 开始计算

### 6. 考勤

考勤类型：

| 类型     | 枚举     | 前端显示 |
| -------- | -------- | -------- |
| 正常出勤 | NORMAL   | 数字成绩 |
| 请假     | LEAVE    | J        |
| 旷课     | ABSENCE  | K        |

正常出勤：

- 成绩范围为 0 ~ 该节课程最高分

请假 J：

- 先记录 J，之后补课
- 补课完成后，补课成绩作为该次课程最终成绩

旷课 K：

- 该次成绩为 0
- 即使完成旷课补课，该次最终成绩仍然为 0
- 旷课补课未完成的学生进入重修

### 7. 补课

请假补课：

- 补课完成后按照该次课程评分规则获得成绩

旷课补课：

- 补课完成，但最终成绩仍然为 0
- 补课最高分允许配置

### 8. 助教额外参加

- 额外参加记录必须保存具体明细
- 不能只保存一个 extra_count 数字作为真实数据
- 额外参加次数由明细记录统计
- 额外参加次数按学期独立统计
- 不能抵扣正常劳动课程要求次数

### 9. 成绩

四项成绩：

1. 劳动实践
2. 课程报告
3. 理论学习
4. 项目实践

默认权重：

| 项目     | 默认权重 |
| -------- | -------- |
| 劳动实践 | 55%      |
| 课程报告 | 10%      |
| 理论学习 | 15%      |
| 项目实践 | 20%      |

约束：

- 四项权重总和必须为 100%
- 最终成绩 = 四项成绩 × 对应权重后求和
- 最终结果四舍五入为整数
- 换证考试不参与四项成绩汇总

说明：

- 课程报告、理论、项目实践暂时只保存最终成绩，不设计复杂过程评分

### 10. 重修

重修原因包括：

1. 成绩不及格
2. 劳动次数不足
3. 旷课补课未完成
4. 严重行为问题
5. 教师手动指定

约束：

- 教师手动指定重修时必须填写原因，最多 50 字
- 重修不能覆盖原始历史成绩

### 11. Excel 导入导出

- 支持基础数据和成绩导入
- 错误数据必须记录：Excel 行号、学号、错误类型、错误原因
- 正确数据不能因为其他行错误而全部失败

### 12. 封存

- 课程实际发生日期 + 10 个自然日自动封存

封存后：

- 普通教师和助教不能直接修改

如确需修改：

1. 提交修改申请
2. 填写原因
3. 授权人员审批
4. 获得限定修改时间
5. 完成修改
6. 写入操作日志

## 四、编码规范

### Java

- 类名使用 UpperCamelCase
- 方法和变量使用 lowerCamelCase
- 数据库字段使用 snake_case
- Entity 与数据库字段明确映射
- DTO 与 VO 分离
- Controller 不直接处理复杂业务逻辑
- 业务逻辑放 Service
- 数据访问放 Mapper
- 统一异常处理
- 统一返回结果结构
- 关键业务增加参数校验
- 所有枚举建立独立 Enum 类
- 不要在业务代码中大量使用字符串硬编码表示状态

---

## 五、数据库规范

- 数据库表名使用 snake_case
- 主键统一：BIGINT AUTO_INCREMENT
- 时间字段统一：DATETIME
- 日期字段：DATE
- 存储引擎：ENGINE=InnoDB
- 字符集：DEFAULT CHARSET=utf8mb4
- 排序规则：COLLATE=utf8mb4_unicode_ci
- 所有核心外键建立索引
- 重要业务关系建立 UNIQUE 约束
- 禁止使用数据库级联删除破坏业务历史数据

---

## 六、日志规范

关键业务操作必须可以追踪。

后续阶段使用 operation_log 记录：

- 新增
- 修改
- 封存
- 修改授权
- Excel 导入
- Excel 导出
- 重修判定
- 成绩计算
- 补课成绩修改
- 权限变化

日志保存修改前值和修改后值。
