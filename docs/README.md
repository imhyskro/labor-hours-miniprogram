# 劳动学时管理系统文档中心

本目录保存需要与源码共同维护的项目文档，主要回答四类问题：系统要解决什么业务、各角色可以做什么、开发应遵守哪些规则、数据库如何承载这些业务。这里不是临时材料或会议附件的存放区，进入本目录的内容应能独立说明其主题，并可作为设计、开发、测试和验收的依据。

## 文档结构

```text
docs/
├── README.md                # 文档范围、阅读顺序和维护规则
├── PROJECT_RULES.md         # 业务规则与开发约束基准
├── DEVELOPMENT_PHASES.md    # 模块拆分、阶段目标和交付记录
└── sql/
    ├── README.md            # 数据库模型、导入规则和执行说明
    ├── 00_rebuild_schema.sql
    ├── 01_seed_reference.sql
    └── 02_verify_schema.sql
```

## 各文件职责

| 文件或目录 | 主要内容 | 适用人员 | 不应承担的内容 |
| --- | --- | --- | --- |
| `PROJECT_RULES.md` | 角色权限、课程、考勤、补课、成绩、封存、日志等业务规则 | 需求、开发、测试人员 | 运行命令、个人任务记录、未经确认的设想 |
| `DEVELOPMENT_PHASES.md` | 模块拆分、阶段目标、交付物和进度 | 项目负责人、开发人员 | 替代正式业务规则或数据库定义 |
| `sql/README.md` | 数据库范围、核心实体关系、Excel 导入契约、事务和维护规则 | 后端、数据库、测试人员 | 保存数据库账号密码或本机连接信息 |
| `sql/*.sql` | 建库、基础配置和结构检查语句 | 后端、数据库人员 | 临时查询、个人测试数据和不可重复执行的手工修补语句 |

## 推荐阅读顺序

首次接触项目时：

1. 阅读仓库根目录 [README.md](../README.md)，了解系统组成和运行方式。
2. 阅读 [PROJECT_RULES.md](PROJECT_RULES.md)，理解术语、角色边界和关键业务规则。
3. 阅读 [sql/README.md](sql/README.md)，理解数据模型、导入格式和数据库约束。
4. 阅读 [DEVELOPMENT_PHASES.md](DEVELOPMENT_PHASES.md)，了解模块拆分和实施顺序。
5. 再进入 `backend`、`labour-course` 或 Web 管理端处理具体任务。

按岗位使用时：

- 需求与项目负责人重点维护业务范围、术语、角色权限和验收条件。
- 前后端开发人员在实现功能前同时核对业务规则、数据库字段和接口契约。
- 测试人员依据规则和验收条件准备账号、数据和异常场景，不以页面暂时表现反推需求。
- 数据库维护人员执行脚本前必须阅读 `sql/README.md` 中的破坏性操作和执行顺序说明。

## 内容适用顺序

同一业务出现描述冲突时，按以下顺序处理：

1. 已评审确认的正式需求及项目负责人书面确认；
2. 与正式需求同步后的 `PROJECT_RULES.md`；
3. 数据库设计和接口契约；
4. 页面实现、代码注释和阶段记录。

代码已经存在不代表其业务含义必然正确。发现文档与实现不一致时，不应静默选择其中一方，应记录冲突、确认业务结论，再同步修改受影响的需求、数据库、接口、前端和测试材料。

## 文档维护规则

### 业务规则变更

角色权限、业务流程、状态、计算公式或删除规则发生变化时，应更新 `PROJECT_RULES.md`，并检查以下内容是否受影响：

- 数据库表、字段、索引、约束和基础配置；
- 后端 DTO、Entity、Service、权限校验和接口返回；
- Web 或小程序的入口、表单、校验和错误提示；
- 测试数据、测试用例和验收标准。

### 数据结构变更

修改 `sql/00_rebuild_schema.sql` 时，应同时：

1. 更新 `sql/README.md` 中的字段含义和关系说明；
2. 检查 `01_seed_reference.sql` 是否需要新的默认配置；
3. 检查 `02_verify_schema.sql` 是否覆盖新的表和约束；
4. 同步后端资源目录 `backend/src/main/resources/db/v2` 中的部署副本；
5. 标明对既有后端实体、Mapper、Service 和接口的迁移影响。

### 接口或页面变更

接口文档应明确请求方法、路径、角色权限、参数、响应和错误码；页面说明应明确使用角色、终端、入口、前置条件、处理规则、成功结果和失败结果。接口与页面存在一对多或暂不接入关系时，应明确标注，不能用“已实现”笼统代替。

## 术语和写作要求

- 一个术语只表达一个业务概念；“班级”“周次”“课次”“节次”等词必须沿用已确认定义。
- 标题说明文档本身的主题，不使用“修改版”“新版”“整理后”等无法长期维护的名称。
- 正式文档直接陈述有效规则；历史原因和变更过程只在确有追溯价值时单列说明。
- 所有路径、表名、字段名、接口路径和枚举值使用代码格式标记。
- 未确定的业务不得自行补全，统一标记为“待确认”，并写明需要确认的问题。
- 示例必须与规则一致，不得用示例创造新的业务约束。

## 不应存放的内容

- 数据库密码、JWT 密钥、AppSecret 等敏感配置；
- Word/PDF 转换生成的图片、缓存和临时文件；
- 个人每日记录、聊天截图和未整理的会议附件；
- `target`、`node_modules`、IDE 配置等构建或工具产物；
- 与正式脚本混在一起的临时测试 SQL；
- 已失效但没有归档说明的重复文档。

运行后端和微信小程序的方法以仓库根目录 [README.md](../README.md) 为准；数据库的具体执行和设计说明以 [sql/README.md](sql/README.md) 为准。
